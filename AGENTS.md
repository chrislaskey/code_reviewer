# Agent Instructions: Rust Production Application Architecture

## Architecture Overview

This is a Cargo workspace with three Rust crates: `core/` (`app_core`, the shared application logic), `axum/` (`app_web`, the HTTP server wrapping core), and `tauri/` (`app_tauri`, the desktop and mobile app wrapping core). The shared Svelte frontend lives in `svelte/`; its pages call `svelte/src/lib/core/`, which picks the Tauri commands inside the app and the HTTP API in a browser, so pages never call `invoke()` or `fetch()` directly. The web server carries other apps beside the application (`public`, `accounts`, `support`, `forum`, `ops`), each with its name on its tables, core module, API path and page folder, and only `app_` tables sync, but `accounts_preferences`, a person's own choices (`docs/design/locales.md`): the design is `docs/design/multi-app.md`, read it before adding a table or a route. The public website is plain HTML pages in `svelte/src/public/` (`docs/design/public-pages.md`). Core is organized as `data/` (each table's schema and low-level context: baseline validation and its reads and writes), `services/` (clients for other services), `helpers/` (generic functions), and one directory per app (`app/`, `accounts/`, `ops/`) for its high-level contexts, with `database.rs`, `deployment.rs`, `jobs.rs` (the recurring jobs, an app's own listed in `core/src/app/jobs.rs`), `server_tasks.rs` (the tasks the server runs while it is up, an app's own listed in `core/src/app/server_tasks.rs`) and `sync/` (push, pull, events, conflicts, purge, and the `SyncedTable` trait each synced table implements, listed in `core/src/app/synced_tables.rs`) at the root; callers name each module where it lives, with no re-exports: the design is `docs/design/code-organization.md`. Axum and Tauri mirror core: a route handler and a Tauri command sit at the path of the core module they call (`axum/src/app/posts.rs`, `tauri/src/app/posts.rs` for `core/src/app/posts.rs`), and each crate's own machinery (config, auth, the device's accounts and sync, native code) sits at its root: the design is `docs/design/code-organization-axum-tauri-svelte.md`. To add an app feature: add the function under `core/src/app/`, expose it as an Axum route and a Tauri command at the same path, add it to both files under `svelte/src/lib/core/`, then use it in the shared pages. Public application operations take a `Deployment` (the database and its role, server or device) and own their transactions; the contexts under `core/src/data/` borrow the transaction and own private SQLite/PostgreSQL adapters; synced business writes are events (`core/src/sync/events.rs`, records in `core/src/data/app_events/`) so the apps' databases sync with the web server, the system of record: the design is `docs/design/offline-sync.md`, read it before touching a write path or a migration. A person may use the app before signing up, as a local user on a device, who never syncs, or a trial user on the web, deleted after two days unless they sign up; the pages tell them apart by the current user's `kind`: the design is `docs/design/accounts-local-and-trial-users.md`.

## 2. Verification Toolchain Commands
AI Agents MUST run these commands to test, lint, and verify code before declaring a task complete. Never skip these steps. `bin/lint` runs all but the tests, and the pages' checks too: `pnpm check` and `pnpm translations:check` in `svelte/`.

* **Format Check:** `cargo fmt --all -- --check`
* **Linter (Fail on Warnings):** `cargo clippy --workspace --all-targets -- -D warnings`
* **Test Suite:** `cargo test --workspace --all-targets`
* **Security Audit:** `cargo audit`

**Artifacts:** Save screenshots, page previews and other files made for the user to look at in the folder `bin/artifacts` prints: `<main checkout>/artifacts/<project>/<worktree>/`, kept outside the worktree so the app run from the main checkout sees them (see `artifacts/README.md`). Git ignores them, and `bin/dev` in the main checkout serves them at `/artifacts/<project>/<worktree>/<file>` (its port is 1420 unless PORT is set; the user can also reach it from a phone over Tailscale). Give the user the file's URL.

**Asking Questions:** Do not use the `AskUserQuestion` tool or other interactive terminal prompts. This repo is often worked on through the code reviewer app's chat, whose textarea input can't answer them. Ask questions and discuss options in plain text in your normal response, then wait for the user's reply.

## 2a. Template and App Code
This repository is a template; apps are copies of it that merge its updates and send changes back. `framework.toml` sorts the files: **framework** (the template's machinery), **seams** (files every app edits to add a feature: the lists of synced tables, jobs, routes, commands and nav) and **examples** (posts and files, the app's to replace). The design is `docs/design/template-and-apps.md`.
* **Before editing a framework file**, prefer extending it from the app's own files: a synced table implements `SyncedTable` and is listed in `core/src/app/synced_tables.rs`; a table with bytes implements `SyncedBytes`; a job implements `RecurringJob` and is listed in `core/src/app/jobs.rs`; a task the server runs while it is up implements `ServerTask` and is listed in `core/src/app/server_tasks.rs`. A Claude Code hook (`.claude/settings.json`) notes each edit of a framework file.
* **When a framework file must change** in an app, declare it in `framework.toml` as a `[[divergence]]` with the reason, and say so in the summary; a change that would serve every app belongs in the template instead. `cargo test --workspace` fails on a framework file that differs from `framework.lock` without one.
* **In the template itself**, run `cargo run -p framework_check -- lock` after changing a framework file, and put generic changes in their own commits.

## 3. Strict Architectural Rules
* **Naming** Always use concrete naming instead of jargon. Better to have an explicit name that tells what happens when it is called instead of a shorter name with jargon and ambiguity. Prefer concrete terms like list/get/create/update/upsert/delete on Backend and index/show/new/edit/delete for UI/UX.
* **Resource first, then the action**, in every layer, so names sort and read by resource. In Rust the resource is the module and the action the function, called through the module as the standard library does (`posts::list`, never `list_posts`, and never a bare `list` imported on its own). Where one namespace spans every resource the two join as `posts_list`: Tauri command names (`pub async fn posts_list`, which is its name on the wire too), test names (`posts_get_missing`), migration names (`posts_create`). In JavaScript they join as `postsList`, `postsShowUrl`; Svelte pages are `PostsShowPage`. HTTP routes are resource first by their paths (`/api/posts/:id`).
* **Scope** Better to build through many small, well-defined iterative steps than try to build everything at once. Do not add product features or functionality that hasn't been discussed and planned first - instead write suggestions for additional functionality in `docs/suggestions/*.md` files.
* **Rust vs JavaScript** Keep the JavaScript frontend a very thin presentation layer. Prefer writing application logic in Rust whenever possible, minimal logic in JS just related to presentation layer.
* **Pages:** one dedicated page per URL, in the folder of its path (`/accounts/products/:id` is `svelte/src/accounts/products/AccountsProductsShowPage.svelte`), with RESTful paths and names: `index`, `show`, `new`, `edit`; a singular resource has no id (`/profile/edit`). A folder's pieces that several of its pages share, or that are large enough to stand alone, go in its `components/` (`posts/components/PostsForm.svelte`); a small piece used once stays in its page. The app's frame (header, nav, menus, banners) is `svelte/src/lib/layouts/`. A page loads what it shows with `loaded()` (`svelte/src/lib/loaded.svelte.js`), `{ reloadOnSync: true }` where another device's change should appear, and shows a thrown error with `errorMessageOf()`. State several components share is a `$state` object in a `.svelte.js` module, read as `currentUser.value`, never copied into each page or passed down as props. Every word a person reads or hears goes through ttag: `t`, `ngettext` for a count, `jt` with `TranslatedParts` for a sentence with a link in it, called as the page draws, never in a module constant; `pnpm translations:check` fails otherwise (README, Translations).
* **Core components:** `svelte/src/lib/components/` holds mostly atoms, the small elements every page uses, imported from its `index.js`: `Heading` (the page's title at level 1), `Text`, `ErrorMessage`, `Button`, `Link`, `Label`, `Input`, `Textarea`, `FileInput`, `Checkbox`, `Badge`, `Alert`, `Panel` and `Icon`; and the generic pieces many pages repeat: `Page`, `Dialog`, `DialogActions`, `FieldErrors`, `TileGrid` and `TranslatedParts`. Use them for the elements they cover, never a raw `<h1>`, `<p>`, `<button class="btn">`, `<a class="link">` or `<input class="input">`, so the small stuff looks the same everywhere. Everything bigger is built freely from them: a `<div>` with Tailwind utilities for a layout, a component of a page's own, or one that knows the app and is shared across folders in `lib/` (as `FileImage` and `AccountsNeeded` are). Composing from atoms is the default because it stays flexible; a molecule joins the core components only once the same combination is reused across many pages. When an atom doesn't do what a page needs, add an option to it (a prop or a variant) rather than restyling the element on that page. When a new atom seems needed, or an option doesn't fit, ask before building it, or, when working without the user, build it and flag it in the final summary for review.
* **Record access:** Application workflows call the contexts under `core/src/data/` rather than issuing SQL. A `data` module has its table's name (`data/app_posts`) and holds the schema, its baseline validation (an `Accepted*` row made by validating, as an Ecto changeset) and its reads and writes; writes to synced `app_` tables stay `pub(crate)`, since each is an event. Keep atomic bulk lifecycle and maintenance operations explicit there; their exceptions and hook limits are documented in `docs/design/low-level-contexts.md`. Database connection/migration setup and test fixtures are separate.
* **Module Layout:** Follow standard Rust layouts. Keep `main.rs` or `lib.rs` thin. In core, a table's records go in `data/`, a client for another service in `services/`, a generic function in `helpers/`, and logic over several resources or services in its app's directory (`app/`, `accounts/`, `ops/`), see `docs/design/code-organization.md`.
* **Workspaces:** If adding features spanning multiple domains, separate them into dedicated crates within a Cargo workspace.
* **State Management:** Web/API handlers must pass shared state via thread-safe atomic wrappers (`std::sync::Arc`) or Layered Extractors. Avoid global mutable state (`lazy_static`/`once_cell` for mutable variables).

## 4. Code Style & Idioms
* **Naming:** Variables/Functions/Modules = `snake_case`; Structs/Traits/Enums = `PascalCase`; Statics/Constants = `SCREAMING_SNAKE_CASE`.
* **Clarity over Cleverness:** Prefer explicit, readable imperative or clear functional styles (`Iterator` chains). Avoid over-engineering hyper-complex lifetime definitions unless performance profiles demand it.
* **Clarity over Performance:** Prefer clear well structured code over optimizing for raw execution speed.
* **Clippy Alignment:** Strictly conform to standard clippy settings. Fix all suggestions.
* **Code Comments** prefer self documenting using good naming conventions for modules, functions, and variables. Only use comments to explain when absolutely critical. Always keep comments very short and concise.

## 5. Explicit Type & Error Handling
* **No Swallowing Errors:** Production code MUST NOT use `.unwrap()`, `.expect()`, or `panic!` unless writing test suites or mathematically proven unreachability.
* **Crate Stack for Errors:** 
  * Use `thiserror` for domain-specific, strongly-typed library errors.
  * Use `anyhow` with descriptive `.context()` additions only at the application execution/CLI boundary layer.
* **Propagations:** Prefer the `?` operator over exhaustive macro-matching unless matching yields explicit domain logic.

## 6. Async & Concurrency Guardrails
* **Tokio Runtimes:** Never hold a standard `std::sync::MutexGuard` across an `.await` boundary. This freezes thread executors. ALWAYS substitute with `tokio::sync::Mutex` if a lock must be held across a yield point.
* **Blocking Tasks:** Do not execute heavy synchronous I/O or intensive CPU tasks directly inside async runtime threads. Intercept and wrap them via `tokio::task::spawn_blocking`.

## 7. Operational Boundaries (Three-Tier Enforcement)
* **ALWAYS DO:** Document public structs and functions using triple-slash (`///`) doc comments. Document safety guarantees with an explicit `// SAFETY:` block whenever `unsafe` is utilized.
* **ASK FIRST:** Prefer to use common libraries instead of writing our own, ask the user before writing our own version. Ask before altering database schemas / core migrations / deployment / git actions.
* **NEVER DO:** Never commit hardcoded API secrets, credentials, or development `.env` configurations. Use the `secrecy` crate or environment mapping wrappers.
