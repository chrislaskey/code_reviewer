# Using an Elixir workflow engine with Svelte, Tauri and Axum

**Superseded by [the backend seam](../design/backend-seam.md).** The `phoenix/` links below point at a directory removed after `f100d21`.

**Design proposal.** Give the existing Elixir engine authority over one workflow from request through completion. Keep Svelte as the shared UI, Axum as the public HTTP boundary, and Rust core as the device's SQLite application layer. Start with a workflow that already has an aggregate, a meaningful business decision and a visible outcome. A signed-in user should be able to request it, disconnect, and later see the same outcome on another device.

The deciding question is **what the server promises when it answers a write**. For example, accepting a request to submit a review can be immediate and durable. Finishing the review can take hours. The app can show both accurately. Treating a job insertion as a completed review would let the phone discard its only pending edit and display a result the engine might subsequently refuse.

This assessment uses the Rust application in this checkout and the documented behavior of Commanded and Oban. The deployed engine's commands, event schema, store adapter, library versions and recovery guarantees need confirmation. The checkout's Phoenix example has its own Ecto event flow, a push that accepts rows alongside events, and a different backfill URL. Its dependency files do not list Commanded or Oban. It illustrates a previous approach to sync and shared validation. ## What already fits

| Part | What the checkout does today | What adopting the engine changes |
| --- | --- | --- |
| Svelte | Pages use the same JS API. Its browser and Tauri implementations choose HTTP or native commands. | Add workflow operations there. Pages display locally queued, server-decided and workflow-completed states when relevant. A browser write already has a network boundary. Offline browser editing would be a separate feature. |
| Tauri and core | A device writes its SQLite row and queues its edit in one transaction. Sync runs for the active account and its selected server. Pages can reload after sync. | Keep local validation and durable drafts. For a workflow action, keep the person's intent and last confirmed state distinguishable across app restarts. |
| Axum and core | Web handlers call the same application functions as devices. A server write can update several rows and record its answer in one local transaction. Sync push applies each input in order in its own transaction. | Route **both** web actions and device submissions for a migrated workflow to the same Elixir command. A network call introduces a second failure boundary. An enclosing Rust transaction cannot roll back an Elixir decision. |
| Device sync | Push returns a per-input verdict. Pull and community backfill deliver authorized rows. Registered tables handle dependencies, conflicts, pruning and purge. | Publish an authorized row-shaped workflow view. Keep domain history, worker arguments, and intermediate private data inside the service. |
| Existing server features | Rust owns accounts, memberships, preferences, files, purchases and recurring maintenance. The server supports SQLite or PostgreSQL. | Keep these owners in the first integration. Oban can run workflow jobs alongside the existing Rust scheduler if each job has one owner. Inventory any dependency the chosen workflow has on membership, deletion, uploads or plans. |

## Choose the boundary before choosing the transport

| Approach | Advantages | Costs and when to choose it |
| --- | --- | --- |
| Rust owns the business decision and sends work to Elixir | Smallest change for background computation. The existing offline edit, field merge and answer remain coherent. | Needs a durable handoff after commit and a return path for results. Fits when Elixir performs an effect or calculation. If its aggregate can veto the business decision, Rust cannot promise that decision to the client. |
| **Elixir owns a workflow, Axum fronts it** | Reuses the existing aggregate invariants, history, process managers and workers. One decision path for browser, phone and timers. Other app features keep their existing guarantees. | Adds a private service call, cross-language contract tests and a projected read model. Best first choice when the workflow engine is already the authority and its inputs can be expressed as commands. |
| Elixir owns every synced write | One server-side decision model across the application. Axum can still own sessions, static assets and the public contract. | Requires reproducing the semantics of each registered table, rebuilding access and deletion paths, and migrating existing devices and data. Most expensive for apps that currently deploy just a Rust binary with SQLite. Consider only if workflows govern most writes and several pilots demonstrate a common contract. |

A private request/response API is sufficient for the pilot. Axum authenticates the person, supplies a deployment-scoped actor to Elixir over an authenticated service connection, and supplies a stable request ID. Domain facts return through a durable subscription. Keep requests bounded in time and let Oban do the long-running work. Embedding BEAM in Tauri, adding a public Phoenix endpoint or introducing a broker would each solve a different problem. None is a prerequisite for this split.

## Follow one submission through the system

Consider an illustrative review with a draft, a submission deadline, and a background check. Substitute an actual aggregate from the engine before implementation. The words **queued**, **submitted** and **completed** have different evidence behind them.

1. **A person taps Submit offline.** Rust checks the draft's shape and required fields. It saves a stable submission ID, the review ID, the last confirmed revision and the intent in SQLite alongside the display change. The screen says “Waiting to submit.” The user can close the app. Submissions that require a live entitlement or cannot sensibly be deferred can instead be online-only.
2. **The device reconnects.** Tauri sends the intent to Axum for the active account. The web button reaches the same command via Axum. A browser must also retain the request ID across a timeout or repeated click. Axum derives the actor from authentication. The engine checks present authority and evaluates the deadline, expected state and other business rules at a defined decision point.
3. **The aggregate decides.** For an open review it persists a fact such as `ReviewSubmitted` carrying the submission ID and the new revision. For a review that closed while the phone was offline it returns a recorded refusal with a stable reason and the current state the actor may see. Submitting the same intent again must recover the decision, including a partial conflict or refusal where applicable. A timeout means the outcome is unknown.
4. **The app reconciles.** Axum returns a terminal sync answer only when it has the decision and can provide the corresponding authorized row required by the operation. Rust retires that intent, installs the confirmed state when safe, and preserves later queued edits. The browser can show the returned state immediately. A stale list response must not move it back to draft. If the read model has not caught up, wait for the specific projection with a bound or return a retryable transport failure and recover using the same ID.
5. **The workflow continues.** A process manager may coordinate dependent commands. An event handler schedules the check in Oban. The worker reports success or permanent failure through another idempotent command. A projection publishes the resulting status. The second device sees that status on pull, even if the first phone never opens again.

Commanded persists events on successful event-producing dispatch. Its default consistency allows reads to lag. Strong consistency can wait for configured handlers, but the append and projection still have separate transactions. An Oban retry has its own lifecycle. Keep a command receipt for “submitted” and a workflow status for “check completed.” [Command dispatch](https://commanded.hexdocs.pm/commands.html) · [Event handlers](https://commanded.hexdocs.pm/Commanded.Event.Handler.html) · [Process managers](https://commanded.hexdocs.pm/process-managers.html) · [Oban retries](https://oban.hexdocs.pm/error_handling.html)

## Which conflicts can Elixir resolve?

| Incoming intent | Server decision | What the person sees |
| --- | --- | --- |
| Two devices edit independent draft fields | For fields explicitly declared mergeable, compare each supplied base value to current state, apply safe edits, then validate the whole resulting draft. | Both edits survive and the next pull converges. |
| Two devices change the same draft field from A to B and C | If B committed first, keep B and return B and C for the conflict. A stale write whose proposed value is already current can succeed as a no-op. | The person can discard C or submit it as a fresh edit against the current draft. |
| One action approves while another cancels | Serialize the decisions on the workflow stream. Evaluate the second action against the resulting state and its prerequisites. | A business explanation such as “Already cancelled.” Offer only actions currently allowed. A generic “reapply status” button would bypass the workflow. |
| Access was revoked offline | Check current access before deciding and before returning any snapshot or receipt detail. Prune data that is no longer visible during sync. | The user learns the action could not proceed. Private values from another member's record stay on the server. |
| A check fails after submission | Record the workflow failure or the engine's compensating action. The original submission remains accepted. | The workflow page explains the failed step and any permitted retry. The sync queue stays clear. |

The existing Rust field merge is suitable for independent data. A client-supplied `base` is a merge aid. It conveys no authority to change owners, workflow state or entitlements. Commands such as approve, cancel and transfer need explicit intent, even when two actions would write the same status field. A single aggregate can serialize its own decisions. For a rule spanning aggregates or a Rust-owned resource, choose a reservation, a single decision owner, or a compensating process and describe the intermediate state. ## Where the integration costs are

**Validation.** Keep cheap, deterministic shape checks in Rust for immediate feedback. Run all authoritative checks again on the server, including current permissions and valid state transitions. Start with shared examples of input, normalization, stable field error codes and expected outcomes in both languages. Version these examples with the command contract. Translate reasons at the UI boundary. If a pure rule proves costly to maintain twice, the Phoenix tree has a precedent for sharing Rust validation through a native extension. That adds native build and release coupling and still leaves authorization and concurrency with the server. [Phoenix validation boundary](../../phoenix/lib/app/data/universal_changeset.ex)

**Reads and sync.** Materialize the workflow view in the database Axum serves. A command can return its aggregate version so the submitting phone can tell when that particular view catches up. For the next sync protocol, give each change in a deployment’s sync feed a durable integer called the **global sync version** (`global_sync_version`). A device saves the version it has pulled through. A Rust-only server assigns these versions as it commits device-visible changes. In a mixed deployment, Rust writes and Elixir projections publish into the same ordered feed. A projector records its source checkpoint with its output so it can resume safely. If the engine uses another database, make that final publication through a durable handoff. The Rust foundation ships first with a fresh schema and a required development reset. [Rust implementation plan](../design/global-sync-version-build.md) · [Projection lag and cursors](elixir-workflow-contract.md#make-pull-safe-when-projections-lag)

**Online-only writes.** A server-only resource can keep its direct write path. What matters for sync is whether the write changes a row or access rule that a device mirrors. For example, signup writes private account data and also creates a public-facing app profile. Only the device-visible consequences need a global sync version. A mobile page can also fetch an online resource directly or keep a separately refreshed cache. [Examples and scope](elixir-workflow-contract.md#which-direct-writes-need-a-global-sync-version)

**Authorization across services.** Keep account credentials at the existing boundary. Include the trusted deployment, actor, resource and operation in the private call. Define how Elixir obtains sufficiently current membership and how a revocation racing an approval is ordered. A cached role is inadequate for an action that must stop the instant revocation takes effect. A synchronous permission lookup alone also leaves a race before append. Give such a rule a shared version or serialization point, or narrow the pilot to actions with a tolerable authorization window. Apply visibility filtering to push replies, pulls, backfills and duplicate-request lookups. [Community visibility](../design/offline-sync.md) · [Server selection and trust](../design/multi-server.md)

**Deployment and operations.** An Elixir release, its event store and its job infrastructure become dependencies of the migrated workflow. Deployments that enable Commanded require PostgreSQL for the production event store. We accept that server dependency. Rust-only servers can use SQLite or PostgreSQL. Tauri keeps SQLite on mobile and desktop in either deployment. Confirm the existing engine's adapter configuration and backup requirements before integration. Scope an engine outage to workflow operations wherever possible. Correlate the client request, aggregate, event, projection checkpoint and job using IDs. Measure oldest undecided request, projection lag, exhausted jobs, and time from a user action to visible confirmation. Document who can reconcile an ambiguous effect and how to restore and replay without contacting providers again. [Existing database configuration](../../axum/src/config/database.rs) · [Commanded production event store guide](https://commanded.hexdocs.pm/choosing-an-event-store.html)

**Retention.** Today the server purges old deletions and can ask a device to resync. Account deletion and trial expiration have consequences beyond hiding a row. Decide what remains in engine history, receipts, job arguments, projections and backups. Prefer opaque references for content that must be erasable. A rebuild must honor deletion and revocation before serving reads. Keep retry evidence long enough for offline devices, or specify what happens to intents older than that window. [Purge implementation](../../core/src/sync/purge.rs) · [Account deletion design](../design/accounts-delete.md) · [Local and trial accounts](../design/accounts-local-and-trial-users.md)

## Recommendation and decision point

First connect one **online** command to the existing engine through Axum. Use it to prove how to recover a committed decision after losing the reply and how a second reader sees it. Then add offline submission for the same command and exercise it with two devices. This order exposes engine and projection assumptions before they become a mobile protocol commitment.

Expand only if the pilot preserves offline intent across crashes, converges without data leakage, and meets an agreed confirmation-latency budget under normal load and projector delay. If a domain has straightforward CRUD with useful field merging, the existing Rust path already supplies that behavior with one ruleset and one deployable server. If several workflows pass the pilot, their common requirements can justify a reusable template seam. The [decision questions and acceptance scenarios](elixir-workflow-contract.md#questions-to-settle-before-implementation) define what evidence to gather first.
