# Elixir workflow integration contract and open questions

Companion to [Using an Elixir workflow engine with Svelte, Tauri and Axum](elixir-workflow-backend.md). This is a proposed contract for one pilot. The engine team can use the questions below to identify which guarantees already exist.

## Map the three kinds of record

| Record | Who creates it | Identity and meaning |
| --- | --- | --- |
| Device edit or workflow request | Rust on a device, or the browser through its web API | A stable request ID identifies one attempt by a person to change something. Retransmission reuses it. A deliberate new decision gets a new ID. |
| Domain event | The Elixir aggregate after deciding a command | A fact in an aggregate stream, with its own event ID and stream position. One request can yield zero, one or several facts. Timers and callbacks can yield facts with no device request. |
| Synced row | The workflow projector | The current device-visible representation. It has a row ID and a row version. The feed records its changes by global sync version. A fact may update several rows. A private fact may update none. |

Today a Rust sync `Event` carries `id`, `table`, `row_id`, `type` (create or update), `base_version`, `base`, `changes` and `made_at`. Its ID is suitable as a request key when translating a supported edit. Its clock is informational. The server's `app_events` records answered edits and can lose entries during purge. Replaying that table as the workflow's complete business history would omit both server-initiated actions and purged records. [Wire type](../../core/src/data/app_events/mod.rs) · [Answer and merge types](../../core/src/sync/events.rs) · [Server purge](../../core/src/sync/purge.rs)

### Choosing a wire format

For ordinary editable fields, an Axum adapter can translate the existing table edit into a typed command. For an action like approval, prefer a dedicated operation such as `SubmitReview`. Give it the request ID, target ID, expected workflow revision and versioned action-specific input. Derive the actor and deployment on the server. Return the decision, a stable reason when relevant, the decided revision and an authorized view or a way to retrieve it. Keep the external command schema independent of Elixir module names.

For the first online pilot, a dedicated Axum operation and corresponding Svelte transport methods are enough. For the offline pilot, decide between two concrete designs:

- **Represent the submission as a synced resource** when it has its own identity and meaningful durable lifecycle. A device creates a submission request with that ID. If the server accepts ownership of the request for later decision, its returned row says “received.” The device can clear the *create request* at that point. The later approved or declined status arrives by pull. Duplicate requests, monitorability, and a terminal business outcome are obligations of the server from receipt onward.
- **Queue an explicit command locally** when the action is a verb on an existing aggregate. The recommended choice for a strict approve or cancel operation. Provide a durable command queue, a way to recover its outcome by ID, and an optimistic UI tied to that ID. Reuse the existing account selection, authentication and sync wakeups. Decide how command dispatch is ordered with pending draft edits. For example, submit a specific confirmed draft revision after its edits have been acknowledged. A rejected dependency should block submission and surface the draft to the person.

In the current protocol `Answer.status` is exactly `applied`, `conflict` or `rejected`. A v1 client removes an applied pending event. A conflict can carry the final row plus individual `yours` and `server` values. Some rejections with a server row cause the device to replace its local value and clear the edit. An ordinary rejected create without a server row can remove the draft and further pending edits for that row. Preserve the person's input separately when a workflow refusal needs a recovery screen. Overloading a rejection reason also changes retry behavior for certain rejected updates. A fourth “processing” status, typed commands in the existing push, or a new table delivered to an old client all require a compatibility plan. [Device answer handling](../../core/src/sync.rs) · [Conflict actions including reapply](../../core/src/sync/conflicts.rs)

## Recover a decision after the reply is lost

Define the identity of a request as deployment, authenticated actor and request ID. Bind it to the intended resource, action, schema version and canonical input. A matching retry can read its decision. A reused ID with different input fails before dispatch. Authorization still governs which fields the caller may see on a later lookup.

One design to test against the actual engine:

1. Durably claim that request identity with a unique constraint and immutable input. Concurrent callers find the same claim. The owner can resume a stalled claim after a crash.
2. Dispatch with that ID to the same aggregate on every attempt. Record the request ID and its decision evidence atomically with the accepted transition. The aggregate must recognize a repeated request even if the read projection and receipt index are behind. An operation that produces no business event still needs durable decision evidence if its terminal answer must survive a crash. Choose an internal decision record in the stream or an equivalent atomic mechanism supported by the actual store. Apply this rule to terminal refusals as well, so a retry after the deadline or a later edit cannot yield a different decision.
3. Materialize the terminal receipt from that evidence. A crash after the append but before this write leaves a recoverable claim. A worker or retry reconstructs the answer from the original decision. Checking an eventually consistent receipt table before a fresh dispatch, by itself, permits duplicate transitions.
4. Return the original decision and its revision. A separately identified, currently authorized snapshot may be newer. The current Rust duplicate-answer helper already pairs the recorded verdict with the row as it stands on retry. Keep a newer confirmed row from being overwritten by an older receipt. Distinguish an infrastructure timeout from a business refusal so a device retains its request.

Verify these steps against the engine's guarantees before choosing storage. A unique HTTP key, a Commanded correlation ID and an Oban job ID serve different purposes. None alone demonstrates atomic decision recovery. [Existing duplicate-answer behavior](../../core/src/sync/events.rs) · [Commanded dispatch and consistency](https://commanded.hexdocs.pm/commands.html)

### Getting work into Oban and back out

Consume committed facts through a durable subscription. In one local transaction, claim a unique effect ID such as event ID plus effect kind, and enqueue the Oban job. Acknowledge delivery after commit. If that transaction cannot include the queue, commit an outbox record with the claim, then deliver from the outbox using the same effect ID. A crash between the event append and the first handler invocation is recoverable by the subscription. A crash after job insertion and before acknowledgement is recoverable by the unique claim. Commanded documents at-least-once event delivery. Oban supports job insertion in an Ecto multi-operation transaction. [Commanded events](https://commanded.hexdocs.pm/events.html) · [Oban insertion](https://oban.hexdocs.pm/Oban.html)

Pass the effect ID to an external provider that supports idempotency. If a worker crashes after the provider succeeds, the next attempt must retrieve or repeat the same provider operation safely. For a provider without that facility, define how to reconcile an unknown outcome and when a person must intervene. Persist success or exhausted failure via an idempotent command so devices can see it. Oban uniqueness controls job insertion within its configured scope. A projector rebuild should populate a fresh read model with external effects disabled and preserve the independent record of effects already performed. [Oban uniqueness](https://oban.hexdocs.pm/unique_jobs.html) · [Worker errors and retries](https://oban.hexdocs.pm/error_handling.html)

## Make pull safe when projections lag

**Use a global sync version (`global_sync_version`) in the next sync protocol**, including Rust-only deployments. It is a durable integer shared by all resources in one deployment’s sync feed. When the phone saves global sync version 52, it has accounted for every change it was entitled to through 52. A change still waiting in a projector can be published later at 53. This removes clock skew, timestamp ties and the need to guess how long a projector might stall. It adds an ordering point for writers, durable change records, and a retention and upgrade policy.

| Question | Number to use | Scope |
| --- | --- | --- |
| Has the review I submitted appeared in its view? | Dispatch with `returning: :aggregate_version`. Record the handler's `stream_version` with the review projection. | Compare versions for the **same stream**. An accepted revision of 12 and a projected revision of 11 tell the submitting phone exactly what it is waiting for. Keep the synced row's own version for optimistic edits. |
| How far did the projector get through its input? | Commanded supplies `event_number` on the event. With `commanded_ecto_projections`, `projection_versions.last_seen_event_number` belongs to a named projector. | Compare positions from the **same event store and ordered subscription**. A projector that has committed through event 809 may still lag a store at 810. Another projector can be further behind. |
| What can the phone safely skip on its next pull? | The global sync version the server returns after scanning changes already committed to the sync database. | Covers **every producer for that feed**, filtered to the current account's authorized rows. A newer aggregate or input event alone says nothing about whether the phone can read its output. |

Commanded can also wait for a named projector configured for strong consistency when an endpoint needs an immediate read. This serves the submitting client. Other devices still need pull to discover changes from all writers. [Dispatch return and consistency options](https://commanded.hexdocs.pm/Commanded.Commands.Router.html) · [Event handler metadata](https://commanded.hexdocs.pm/events.html) · [Ecto projector checkpoints](https://commanded-ecto-projections.hexdocs.pm/usage.html)

**When could the phone use the event number directly?** If one ordered projector handles the entire mobile feed, its published rows, changes and checkpoint commit together, and pull can enumerate every authorized output through that checkpoint, the source `event_number` can also supply the `global_sync_version`. An event producing several rows needs a deterministic continuation within that event, or delivery of its outputs as one group. Using the highest event accepted by Commanded, or the largest checkpoint among independent projectors, could advance the phone past unpublished work.

**Mixed-writer example.** The phone has synced through global sync version 51. Commanded appends event 810 for review R at stream version 12. Its projector is still at 809. Rust commits a post at global sync version 52, and the phone pulls it and saves 52. When the projector catches up, its transaction writes the review view, records source event 810, and publishes the review at **53**. The next pull after 52 finds the review. Redelivery of 810 recognizes the committed source event and produces no second change. Rust and Elixir can take turns publishing without coordinating their source event numbers.

### How a Rust-only server supplies the cursor

Use one durable counter per deployment feed in the server database. A practical starting design is for the existing business transaction to update the synced row, increment a shared counter row, and record a change identifying the resource and row at the new global sync version. Keep deletions discoverable with tombstones. If one transaction changes three rows, assign three consecutive global sync versions in dependency order and commit all three together. A device keeps generating its existing request UUIDs and base row versions offline. The server commits each global sync version with the change that a device can pull. This works without adding event sourcing to a Rust-only app.

The counter update serializes the short publication step. On PostgreSQL a writer updating the same counter row waits until the prior transaction ends. On SQLite only one write transaction runs at a time. Keep external calls outside that step and measure lock contention. A bare PostgreSQL sequence can hand transaction A 52 and B 53, then B can commit first. A phone saving 53 would skip A when it later commits. Permanent unused numbers are harmless provided no change can appear later below a cursor already issued. [PostgreSQL sequences](https://www.postgresql.org/docs/current/functions-sequence.html) · [PostgreSQL row locking](https://www.postgresql.org/docs/current/explicit-locking.html#LOCKING-ROWS) · [SQLite transactions](https://www.sqlite.org/lang_transaction.html)

For a paged pull, take a committed upper bound when the first page starts. Scan changes after the saved cursor through that bound, with current authorization applied even if access changes between pages. Resume after the last change examined. An empty authorized page can advance past filtered entries once the server has examined them. The phone saves each continuation with the corresponding local changes in one transaction. A new membership triggers backfill of now-visible older rows, and a lost membership triggers pruning. A phone whose cursor predates the oldest retained global sync version needs a fresh authorized snapshot with a matching baseline cursor and its pending work preserved. A feed reset or restore that invalidates saved global sync versions needs a new feed identity or an explicit resync. [Sync table contract](../../core/src/sync/synced_table.rs) · [Offline sync design](../design/offline-sync.md)

**Rust foundation and reset.** Implement the global sync version in the Rust-only server and devices first. The template has no deployed apps to migrate. Rewrite the baseline migrations, bump the wire protocol, and require downstream development databases and device installs to start fresh. Normal resync within the new protocol still preserves pending work. Add the Commanded publisher after the Rust-only paths pass their concurrency and convergence tests. [Rust implementation plan and draft changelog](../design/global-sync-version-build.md)

### Which direct writes need a global sync version?

| Server operation | What the phone needs |
| --- | --- |
| Update a credential or insert a billing webhook receipt with no replicated consequences. | No feed entry. The private row stays server-side. An online mobile page reads permitted information through its API. |
| Complete signup, which writes both `accounts_users` and the synced profile in `app_users`. | Publish the profile for its authorized readers. Credentials and private account fields stay out of the feed. |
| Write `accounts_preferences`, including a language change made on the web. | Publish the change for the owner's devices. This is the explicit exception among `accounts_` tables. The synced table registry identifies it. |
| Grant or revoke access to a community. | Publish the membership change. The affected device backfills or prunes existing content even when the individual post rows were untouched. |
| Update a subscription whose plan Tauri caches separately. | The current plan cache is refreshed by an online API call when stale. It can keep that policy. If immediate offline-replica convergence becomes a requirement, introduce an explicit published projection or invalidation and define its freshness. |

Whether a write comes from a browser, SQL context, Oban worker or Commanded handler does not determine its scope. Trace its effect on device-visible rows and access. In the same database, commit a replicated consequence and its publication together. Across databases, make the obligation to publish durable at the source, then apply it idempotently at the destination. ## Questions to settle before implementation

| Decision | Evidence to bring | Why the answer changes the design |
| --- | --- | --- |
| Which workflow and user promise come first? | One real command, its aggregate and prerequisites, sample success and refusal, normal and worst-case duration. Which actions may be queued offline? | Determines whether a synced request resource, a queued command or an online-only action fits. |
| Where is the atomic decision recorded today? | Actual Commanded and Oban versions, event-store adapter, example stream and duplicate dispatch results, including zero-event outcomes. | Decides whether an adapter is enough or the engine needs durable receipt support. |
| Which fields may merge and which actions require a fresh revision? | Two-device examples from the domain owner, including submit versus cancel and draft edit versus submit. Who resolves the conflict, and can they reapply? | Determines the command boundary, expected revisions and recovery UX. |
| Who authorizes each decision and each read? | Account and deployment ID mapping, membership source, revocation timing, trial limits, permission to see someone else's outcome. | Determines the trust boundary and which data the service can safely project. |
| What does local-only use mean? | Expected behavior for a local account, moving drafts to a synced account, switching servers and losing a token. | Local-only users currently have no sync queue. Moving a draft must not implicitly approve or submit it. Keep queued requests bound to their account and origin. |
| What dependencies cross the service boundary? | Any draft plus attachment, multi-aggregate step, quota, account deletion, or web write that is currently atomic across resources. | Choose prerequisite checks, compensation and which operation owns the commit. For an attachment, prove the bytes exist and the actor may access them before starting work. |
| What read and recovery guarantees do users need? | Latency budgets for acknowledgement, read-after-write and other-device visibility. Longest supported offline interval, retention requirements and projector rebuild time. | Determines synchronous waits, retry evidence retention, cursor design and operating cost. |
| Who publishes every device-visible change? | List Rust writers, source stores, projector names, any parallel subscriptions, and server-only writes with replicated effects. Measure concurrent publication on SQLite and PostgreSQL. | Establishes whether one ordered projector covers the whole feed or a shared publication counter is needed, and sets retention and throughput requirements. |
| Which deployments and client generations must interoperate? | SQLite-only self-hosters, active mobile versions, server origin selection and engine availability. Inventory old queued edits and older event schemas. | Current sync requires an exact protocol version and returns HTTP 426 on mismatch. Pick a compatible endpoint or coordinated upgrade. Version domain events and decide how historical events are read during replay. |
| Who handles failed work after launch? | Named owners for the Axum boundary, aggregate, projection, worker and external effect. A recovery drill for a lost receipt and an ambiguous provider call. | Determines deployment readiness, backup/restore order and who is allowed to retry an effect. |

See the existing rules for [multi-app data](../design/multi-app.md), [account moves](../design/accounts-local-and-trial-users.md), [file bytes](../design/offline-files-decisions.md) and [protocol enforcement](../../axum/src/sync.rs).

## Pilot acceptance scenarios

Run a real Axum–Elixir integration against the engine's actual store, using the browser path and two independent device databases. Keep the Rust in-process sync tests as the baseline for existing resources. Capture the request, decision revision, visible row versions, final device state, and count of external effects for each case.

| Exercise | Passing observation |
| --- | --- |
| Submit from the web. Submit a different review from a phone offline and restart the phone. | Both reach the same decision code. The offline intent survives restart. Each UI distinguishes queued, accepted and completed. The second device converges. |
| Drop the response after append. Retry concurrently. Reuse the same ID with altered input. | One business transition and one effect. A matching retry recovers the same verdict. Altered input cannot inherit the receipt. |
| Edit different fields, then the same field, from two devices. Race approval against cancellation. | Safe edits survive. A same-field collision retains both values for the authorized user. Only allowed transitions occur, including after a manual retry. |
| Submit behind pending draft edits. Refuse an earlier edit. Revoke membership while offline. | Dependencies resolve in order or block visibly. No unintended revision is submitted. A revoked actor receives no private snapshot and the device prunes its copy. |
| Stop the projector after event 809. Pull a Rust write. Publish event 810, redeliver it, then rebuild the read model. | The phone can advance through the Rust write and still receive the later review publication once. A rebuild preserves cursor meaning or explicitly requests resync. |
| Stall the first of two concurrent Rust publication transactions on each supported database. Pull between commits, then repeat with the first writer rolling back. | No change can commit below a cursor already returned. A failed transaction exposes neither its row nor its publication. |
| Write a private credential, change a synced preference online and revoke a membership. Reconnect a protocol-2 device with a pending edit after its cursor falls below retention. | The feed contains only the replicated consequences. The phone bootstraps current visible rows, prunes revoked rows and preserves its pending intent for adjudication. |
| Stop the worker before and after its provider call, lose the callback, then exhaust retries. | A known effect occurs once or an unknown outcome enters reconciliation. The workflow exposes failure and permits only safe recovery. |
| Disconnect the engine mid-batch. Reconnect an older client, then a device beyond the purge horizon. | Previously decided inputs recover by ID, undecided inputs survive, incompatible clients get a clear upgrade path, and resync preserves outstanding user work. Unrelated app operations have the intended availability. |

Start with a new workflow or isolated test cohort so the first pilot needs no historical write migration. For an existing resource, first reconcile an imported baseline with the Rust rows and their revisions, account for already queued edits, and compare projected reads in shadow with external effects disabled. Cut over a bounded set of aggregates to exactly one writer. A rollback after the first Elixir decision must preserve that history. Pause new commands, reconcile decisions and effects, and resume with an owner that can recognize all previous request IDs. Switching traffic straight back to the former writer could accept the same action twice.
